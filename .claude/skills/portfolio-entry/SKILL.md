# Projects 항목 완성

Projects 항목 하나를 스텁에서 발행 가능한 상태로 만든다.

이 페이지가 파는 것은 결과물이 아니라 **판단**이다. `judgment`가 심장이고,
`metrics`는 조건을 못 쓰면 광고가 된다. 그래서 이 스킬의 절반은 "쓰지 않을 것"을
가르는 관문이다.

## 독자 눈높이 — 모든 필드에 걸리는 규칙

**전공자가 아니어도 읽히게 쓴다.** 채용 검토자, 동료 개발자, 협업을 제안하려는
사람이 같은 페이지를 읽는다. 셋 중 누구 하나라도 첫 문장에서 걸리면 그 항목은
없는 것과 같다.

방법은 **설명을 덧붙이는 것이 아니라 같은 길이로 더 쉬운 단어를 쓰는 것**이다.
풀이를 괄호로 붙이면 글이 늘어져 검토자가 안 읽고, 정확도를 낮추면 개발자가
안 믿는다. 둘 다 지키는 지점은 어휘 교체뿐이다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| jetsam 이 터졌다 | macOS 가 앱을 강제로 껐다 |
| 공급자 중립 규약 | 세 도구가 같은 규칙 하나를 읽도록 |
| 정형 작업은 정적 기본값으로 고정 | 판단이 필요 없는 일은 늘 같은 모델로 고정 |
| 전 인터페이스 바인드 HTTP 서버 | 바깥에서 접속할 수 있는 채로 열린 임시 웹 서버 |
| 유예 900초 | 15분이 지난 |
| 내부 은어(D-번호 대장, bin, 슬러그) | 결정 기록, 직접 만든 명령어, 글 주소 |

**남기는 전문어**는 두 종류뿐이다.

1. **고유명사** — Claude Code, Xcode, Git. 바꾸면 부정확해진다.
2. **그 항목의 핵심이라 피할 수 없는 것** — 단, 처음 나올 때 문장 안에서 뜻이
   드러나야 한다. 각주나 괄호 풀이를 달아야 한다면 그건 아직 안 풀린 것이다.

숫자와 사실은 절대 뭉개지 않는다. 쉽게 쓰는 것은 어휘의 문제이지 정밀도의
문제가 아니다. `83GB`, `4분 사이 네 번`, `프로세스 463개` 는 그대로 둔다.

자기 점검: **이 문단을 비개발자 친구가 소리 내어 읽었을 때 되묻는 단어가 있는가.**

## 순서

근거 → 판정 → 초안 → 렌더 검증. **근거 없이 문장을 먼저 쓰지 않는다.** 순서를
뒤집으면 그럴듯하지만 확인되지 않은 문장이 남고, 그건 이 페이지에서 가장 비싼
실패다.

## 1. 근거 수집

대상 저장소에서 다음을 읽는다. 없는 것은 없다고 적고 넘어간다.

- `README.md` — 무엇을 왜 만들었는지의 1차 진술
- `CONTEXT.md`, `docs/adr/`, `docs/decisions/`, `DECISIONS.md` — **judgment 의 광맥**
- `git log --reverse --format=%ad --date=short | head -1` — 실제 시작일
- `git shortlog -sne --all` — 작성자
- `gh repo view <owner>/<name> --json visibility` — 공개 여부

Agent OS 는 `~/.dotfiles/agent-os/DECISIONS.md`(D-번호 대장)가 전부였다. 결정
기록이 있는 저장소는 이 단계에서 사실상 초안이 끝난다.

## 2. 사실 판정 네 가지

스텁에 이미 적힌 값과 기억을 믿지 않는다. 넷 다 실제로 확인한다.

| 확인할 것 | 방법 | 왜 |
|---|---|---|
| **내 작업인가** | `git shortlog -sne --all` 에 본인 커밋이 있는가 | 온보딩·클론해 둔 남의 저장소가 `~/projects` 에 섞여 있다. 실제로 한 건 걸렀다 |
| **visibility** | `gh repo view --json visibility` | `private` 이면 상세 페이지가 "비공개 시스템 · 소스 미공개"를 렌더한다. 틀리면 거짓말이 되고, 링크 가능한 근거를 스스로 가린다 |
| **date** | 첫 커밋 또는 첫 결정의 날짜 | 목록 정렬 축이다. 틀리면 순서가 틀어진다 |
| **links** | 실제 URL 을 열어 확인 | 기본 브랜치가 `main` 인지, 파일 경로가 살아 있는지 |

공개 저장소인데 `private` 로 적혀 있으면 바꾼다. 반대도 마찬가지다.
**비공개인 것이 소스가 아니라 데이터인 경우가 흔하다** — 설계·판단은 공개
저장소에 있고 로그·큐·볼트·사용량만 비공개인 형태.

## 3. 필드별 규칙

### summary

스키마는 200자를 허용하지만 **실제 상한은 70자 안팎**이다. 헤더가
`max-w-[38ch]` 라 그 이상은 벽이 된다. 세 줄을 넘기면 줄인다.

무엇을 만들었는가가 아니라 **무엇이 어떻게 달라졌는가**를 쓴다.

### problem

`whitespace-pre-line` 으로 렌더된다. **한 문단은 반드시 소스에서도 한 줄이다.**
YAML 에서 보기 좋게 접으면 그 줄바꿈이 그대로 화면에 나가고, 좁은 화면에서는
두 번 접혀 누더기가 된다.

도구 자랑이 아니라 마찰 서술로 시작한다. "블로그를 만들고 싶었다"는 문제가
아니다. 무엇이 막혔는지, 그게 왜 불편을 넘어 실제 비용이었는지를 쓴다.

### judgment — 이 페이지의 심장

**항목마다 버린 선택지를 반드시 쓴다.** 신뢰를 만드는 건 성공 서술이 아니라
"무엇을 포기했는지 아는 사람"이라는 증거다.

- **plain text 로 렌더된다.** 마크다운이 안 먹으므로 `**강조**` 는 별표가 그대로
  보인다. 따옴표는 곡선따옴표(`“ ”`)를 직접 입력한다 — 본문(MDX)은
  smartypants 가 변환해 주지만 frontmatter 는 안 거친다.
- **5개가 상한**이다. 그 이상은 벽이 되어 아무도 안 읽는다. 남는 판단은 본문으로.
- 서로 다른 축을 고른다. 같은 결정의 두 측면보다 지시/기록/자원/라우팅처럼
  갈라지는 편이 낫다.

최상급 재료는 **뒤집힌 초안**이다 — 검수 지적을 받아 설계를 바꾼 기록. ADR 의
"이유", "검토 후 유지", "보류" 절에 묻혀 있다.

### metrics

1. `value` 는 문자열. 델타는 `→` 로 쓰고 두 숫자를 다 보여준다.
2. **`note`(조건·분모)를 못 적는 metric 은 싣지 않는다.** 그건 광고다.
3. **3의 배수로 맞춘다.** 데스크톱 3열 그리드다(모바일은 1열).
4. 억지로 채우지 않는다. `metrics: []` 는 정직한 상태고 아무것도 렌더되지 않는다.

성공 지표만 고르지 않아도 된다. 사고 규모·오탐 비율처럼 실패를 정직하게 적은
숫자가 성공 숫자보다 강하다.

### writings

**permalink 가 아니라 bare slug.** `/memo/macos-settings` → `macos-settings`.
없는 slug 을 적으면 `src/lib/projects.ts` 가 빌드 타임에 위치를 짚고 던진다.
연결할 글이 없으면 `[]` — 섹션이 통째로 렌더되지 않는다.

### 시각 자료 — 넣을 때와 안 넣을 때

**무조건 넣는 게 좋은 것이 아니고, 없는 것을 만들어 내면 안 된다.** 그 작업의
산물이 아닌 그림을 포트폴리오용으로 새로 그리는 것은 `note` 없는 metric 을 싣는
것과 같은 실패다. 검토자는 구분한다.

판정 기준은 **“이미지가 있는가”가 아니라 “그게 작동을 보여주는가”**다.
실제로 걸러진 세 가지 실패:

| 있었던 것 | 왜 안 되는가 |
|---|---|
| 스토어 홍보 배너 | 로고와 슬로건이다. 물건이 도는 모습이 아니다 |
| 디자인 QA 캡처 | 실제 화면이지만 내용이 더미(`UI 테스트 · 0페이지`)라 빈 카드로 읽힌다 |
| 앱 아이콘·아바타 에셋 | 재료이지 결과가 아니다 |

넣어도 되는 것은 **그 작업의 결과로 이미 존재하고, 실제 데이터로 도는 모습**뿐이다.
그런 게 없으면 안 넣는다 — 텍스트가 정답이고, metrics 세 칸이 억지 다이어그램보다
강하다. 시스템·CLI·규약 성격의 항목은 대개 여기 해당한다.

이 사이트 고유 제약:

- 스키마에 이미지 필드가 없다. `/portfolio` 목록에는 안 뜨고 **Result 섹션
  본문(MDX)에만** 들어간다.
- 색을 쓰지 않는 사이트다(명도 4단계). 채도 높은 배너·목업은 문법을 깬다.
- 자기 사이트를 다루는 항목에 자기 스크린샷을 넣지 않는다. 검토자가 이미 그
  안에 서 있다.

없어서 안 넣었다면 **왜 안 넣었는지를 MDX 주석에 남긴다.** 다음에 같은 판단을
다시 하지 않기 위해서다.

### 본문(MDX)

`Result` 섹션 아래로 들어간다. 숫자로 안 잡히는 결과와 지금 어디까지 왔는지를
쓴다. 섹션 제목은 페이지가 이미 갖고 있으므로 `##` 를 다시 쓰지 않는다.

스텁의 지시용 주석(`{/* ... */}`)은 지운다. 대신 **스텁의 전제를 뒤집은 결정이
있으면 그 이유를 주석으로 남긴다** — visibility 변경, date 변경 같은 것. 이
저장소의 주석은 "무엇"이 아니라 "왜"를 적는 자리다.

## 4. 렌더 검증

**`pnpm build` 통과는 검증이 아니다.** 스키마만 본다. 반드시 실제로 연다.

```sh
pnpm dev   # http://localhost:3000/portfolio/<slug>
```

확인 항목:

- [ ] summary 가 세 줄 이내인가
- [ ] `problem` 문단이 자연스럽게 접히는가 (소스 줄바꿈이 새어나오지 않았는가)
- [ ] `judgment` 에 별표나 곧은따옴표가 보이지 않는가
- [ ] 문단 사이 여백이 균일한가
- [ ] metrics 그리드가 좁은 화면에서 한 열로 쌓이는가, 가로 넘침이 없는가
- [ ] links 가 실제로 열리는가
- [ ] `/portfolio` 목록에서 정렬 위치가 맞는가 (진행 중 먼저, 그다음 시작일 역순)
- [ ] **전공자가 아니어도 걸리는 단어 없이 끝까지 읽히는가**

가로 넘침 확인:

```js
const d = document.documentElement;
d.scrollWidth > d.clientWidth
```

## 5. 정직성 관문

발행 전 마지막. 하나라도 걸리면 그 문장을 지운다.

- 근거 파일에서 확인되지 않은 사실이 있는가
- `note` 없는 metric 이 있는가
- 버린 선택지가 없는 `judgment` 항목이 있는가
- 본인 커밋이 없는 저장소를 싣고 있는가
- 비공개 데이터(접속 주소, 로컬 경로, 세션 로그, 비용·사용량, 계정 정보)가
  새어 있는가

본인만 아는 부분은 지어내지 말고 **명시적으로 표시해 남긴다.** 빈 자리는
정직한 상태다.
